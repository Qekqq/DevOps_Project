# Метрики модели и дальнейшее переобучение

## Готовность данных и расчётов

По просьбе пользователя новый дашборд **не создаётся**. Подготовлены модули расчёта
по выбранному периоду и публикации отдельных месячных метрик. Они проверены чтением
реальной БД. Новый API и обновлённый экспортер ещё не развёрнуты в работающих контейнерах.
Интерфейс и существующий дашборд не изменены. Ниже описаны
подготовленные данные и план будущих панелей **«Метрики модели»**.

После импорта демонстрационной истории 9 сентября 2026 года: 213 исследований
всего, 113 в окне 11 августа — 9 сентября и 112 с обратной связью в этом окне.
Эталон каждой модели — 536 строк train, обе используют одну обучающую выборку.
200 исследований и их исходы искусственные; подробности и история агрегатов —
в [описании демонстрационной партии](demo-history.md).

Метрики имеют сведения `version`, `dataset_id`, `role`: будущий фильтр Grafana
выбирает конкретную версию и переключает её drift, target и качество прогнозов.
Отсутствующие замеры относятся ко всему потоку исследований, поэтому не меняются
при переключении модели. Пока обе модели используют один эталон и одно текущее
окно, их data drift и target drift закономерно одинаковы.

## Выбранный период и динамика

Согласованы три независимых фильтра: **версия модели**, **период** и **группировка
по дням / по месяцам**. Период по умолчанию — последние 30 дат, но расчёт панели
не ограничен скользящим месячным окном. Считаются исследования по `study_date`,
а не по времени импорта, HTTP-запроса или добавления обратной связи.

- «Сегодня + по дням» даёт одну точку по сегодняшним исследованиям.
- Период из 60 дат + по дням даёт 60 точек, включая пустые интервалы.
- По месяцам используются календарные месяцы. Первый и последний обрезаются по
  выбранному периоду. Например, 12 июля — 9 сентября затрагивает **три** месяца.
- Каждый интервал рассчитывается отдельно. Месячные проценты, F1 и PSI нельзя
  получать простым усреднением дневных значений.
- Матрица ошибок и остальные итоги за весь период рассчитываются отдельно.
- Без исследований точка содержит `null` и статус «Нет данных». При нулевом
  знаменателе метрика также `null`; это не нулевая точность. Счётчики размера
  выборки остаются нулевыми. Ноль отсутствующих замеров при непустой выборке —
  полноценное значение. Недостаточная выборка drift имеет статус «Недостаточно данных».
- При новом фактическом исходе следующий запрос пересчитывает затронутые интервалы.
  Это ретроспектива по сведениям, известным **сейчас**, а не архив того, что было
  известно в прошлую дату. В БД хранится дата исследования без времени: разбивки
  на часы и преобразования даты исследования между часовыми поясами нет.

### Подготовленный API

`GET /monitoring/model-health` (через frontend: `/api/monitoring/model-health`)
доступен только администратору по существующей сессии приложения. Параметры:

| Параметр | Назначение |
|---|---|
| `date_from`, `date_to` | Даты YYYY-MM-DD, обе включены; передаются вместе |
| `group_by=day` или `month` | Группировка, по умолчанию по дням |
| `model_version` | Версия из списка активных моделей; без фильтра — обе модели |

Без обеих дат используется период последних 30 дат UTC, включая сегодня.
Один запрос ограничен 366 датами и временем расчёта; это ограничение нагрузки,
а не фиксированное окно метрики. Неизвестная активная версия возвращает 404,
неверный период — 422, ошибка БД/эталона — 503, без частичных результатов.

Ответ содержит `available_models` для фильтра и `models`. У каждой модели:
`reference` (версия, роль, датасет, размер train), `summary` (итог за весь период),
`points` (агрегаты каждого интервала). Границы точки — `start` и `end_exclusive`.
Три блока: `data_quality`, `data_drift`/`target_drift`, `prediction_quality`.
Последний содержит `metrics` и `confusion_matrix` (`tp`, `tn`, `fp`, `fn`).
Матрица использует ИП, ИО, ЛП, ЛО соответственно. В JSON нет персональных строк
и недопустимых значений NaN/Infinity.

Пример: `/api/monitoring/model-health?date_from=2026-07-12&date_to=2026-09-09&group_by=month`.
Все точки и итог читаются в одной транзакции `REPEATABLE READ, READ ONLY`.
Эталон каждой модели кэшируется только внутри этого запроса.

**Подключение источника к Grafana ещё не сделано.** Этот API — готовый контракт
расчётов; обычный источник Prometheus не вызывает его с фильтрами Grafana.
При создании панелей потребуется связать период/группировку/версию с запросом
к расчётам и сохранить проверку доступа. PostgreSQL также может стать источником
агрегатов, но соответствующая таблица и её обновление сейчас не реализованы.

### Отдельные метрики Prometheus

`ModelHealthCollector` продолжает отдавать текущее скользящее окно **30 дат**
при сборе Prometheus, каждые 30 секунд по конфигурации. Это отдельное назначение:
текущий мониторинг и будущие сигналы. Смена периода Grafana не меняет его SQL-окно.
`scripts/export_model_history.py` и ранее сохранённый CSV содержат именно старую
ретроспективу скользящих окон, а не новые дневные/календарные интервалы.
Для будущих панелей с согласованными фильтрами предназначен API выше.

## Три блока показателей

### 1. Качество данных

- «Отсутствующие замеры по показателям» считает нули **только** в `glucose`,
  `blood_pressure`, `skin_thickness`, `insulin`, `bmi`.
- «Всего отсутствующих замеров» суммирует их. У одного исследования может быть
  несколько отсутствующих замеров, поэтому это не число исследований.
- Допустимые нули, например `pregnancies = 0`, в этот показатель не входят.
- Отдельная контрольная панель NULL должна показывать 0: пропуски запрещены
  валидацией API и ограничениями NOT NULL в БД. Нули-заполнители и SQL NULL различаются.
- Считаются исходные показатели до подстановки медиан в pipeline, один раз на
  исследование, независимо от количества прогнозов и повторных HTTP-запросов.

### 2. Data drift и target drift

#### Data drift

Эталон — **только train-строки конкретной версии модели** из её зарегистрированного
датасета. Связь: `model_versions → training_runs → dataset_rows`; номера строк
берутся из `training_runs.configuration.dataset.row_ids.train`.
Validation и test не входят. Если состав train неизвестен или строки отсутствуют,
расчёт завершается ошибкой, а не подменяет эталон всем датасетом.

Расчёт выполняется отдельно для всех активных champion и challenger. Новая версия
автоматически использует своё разбиение train своего выпуска, даже если остаётся
фоновой. При переключении роли модель продолжает сравниваться со своим эталоном.

Для каждого из восьми признаков рассчитывается PSI по интервалам, построенным
из квантилей эталона. Хвосты за пределами эталона выделены отдельно. NULL и нули
в пяти полях отсутствующих замеров учитываются отдельными категориями, поэтому
ухудшение заполненности тоже может вызвать drift. В остальных полях допустимый 0
участвует в обычном распределении. Повторяющиеся границы объединяются; константный
эталон обрабатывается отдельно. Для нулевых долей используется сглаживание 0,0001.

Если выпуск обучали на снимке обратной связи, исследования с `source_study_id`
из всего датасета выпуска исключаются из новой выборки drift. Качество входов при этом
по-прежнему учитывают все исследования выбранного интервала.

Минимум — 100 исследований с каждой стороны. До этого PSI — NaN и показывается
«Недостаточно данных», а не «Смещения нет». Рабочий порог PSI 0,25 — эвристика
для проверки данных, не универсальная статистическая граница и не вероятность ошибки.
100 наблюдений также не гарантируют статистическую надёжность: повторные исследования
одного пациента могут быть зависимы. Пороги нужно калибровать на стабильных периодах.

Расчёт использует SQL-агрегаты. Персональные строки не загружаются в Prometheus;
экспортер получает счётчики и границы интервалов.

#### Target drift

Target здесь — **фактический класс из обратной связи**, не предсказание модели.
Сравнивается доля класса 1 в интервале с долей класса 1 в эталоне. Метрика — абсолютная
разница долей: 0,10 означает 10 процентных пунктов. Она рассчитывается только при
100 размеченных исследованиях интервала и 100 строках эталона.

Исследования без обратной связи не считаются отрицательным классом. Размер размеченной
выборки показан рядом. Если обратную связь дают избирательно, её доля может не отражать
всех пациентов. Смещение target не доказывает изменение зависимости между признаками
и исходом (concept drift). Изменение прогнозов было бы отдельным prediction drift.

### 3. Качество прогнозов

Подготовлены матрица ошибок и Accuracy, Recall, Specificity, Precision/ПЦПР,
NPV/ПЦОР, F1 за выбранный интервал. Все активные версии сравниваются на общей размеченной
выборке с готовыми прогнозами каждой модели. Исследования из датасетов их выпусков
исключаются, чтобы не оценивать модели на знакомых данных. Размер выборки и нулевые
знаменатели учитываются отдельно; неопределённые метрики — NaN в расчёте,
`null` в API. При выборе одной модели состав общей выборки не меняется.

Новые метрики `diabetes_model_health_classification` и
`diabetes_model_health_confusion_matrix` имеют метки версии, роли и датасета.
Существующий `diabetes_classification_report` остаётся отчётом за всё время.
Автоматическое переобучение не запускается. Блок concept drift исключён из
согласованного состава дашборда.

## DVC, собственный реестр и MLflow

MLflow в текущем проекте не интегрирован. Его задачи частично выполняют:

| Задача | Текущее решение |
|---|---|
| Версионирование файлов моделей и воспроизводимый конвейер | DVC, `dvc.yaml`, `dvc.lock` |
| Метрики и параметры выпуска | `reports/`, сведения в `models/<release>/` |
| Датасет, происхождение и конфигурация обучения | `datasets`, `training_runs` в PostgreSQL |
| Версии моделей и роли champion/challenger/archived | `model_versions`, история смены ролей |
| Проверка и загрузка pipeline | `src/model_registry.py` |
| Текущее качество и drift | Экспортер → Prometheus → Grafana |

Это не полная замена MLflow Tracking: отдельного интерфейса сравнения всех запусков
обучения и интеграции с MLflow Model Registry у нас нет. DVC и MLflow можно сочетать:
DVC отвечает за воспроизводимые данные/файлы, MLflow — за регистрацию и просмотр
экспериментов. При внедрении MLflow Registry надо определить единый источник роли
основной модели, чтобы PostgreSQL и MLflow не выбирали разные версии.

**Кто получает файлы из DVC:** `.github/actions/pull-models/action.yml` вызывает
`python -m dvc pull models` перед тестами и сборкой CI. Локально эту команду
запускает разработчик. Файлы попадают в Docker-образ. Во время работы API и
`kafka-consumer` читают локальные артефакты через `ModelRegistry`; они не обращаются
к DVC на каждый прогноз. Постоянного «потребителя DVC», аналогичного consumer Kafka,
нет: DVC — инструмент версионирования и доставки файлов, а не очередь сообщений.

Источники: [DVC pull](https://doc.dvc.org/command-reference/pull),
[MLflow Tracking](https://mlflow.org/docs/latest/ml/tracking),
[пояснение drift](https://docs.evidentlyai.com/metrics/explainer_drift).
Расчёт PSI в проекте собственный; библиотека Evidently не подключалась.

## Предлагаемый следующий этап: автоматическое переобучение

Планировщик и автоматическое обучение **пока не реализованы**. Подготовленные
расчёты наблюдают данные и ничего не переобучают и не переключают.

Предлагаемая последовательность:

1. Ежедневная проверка качества данных и наличия достаточного числа новых
   размеченных исследований. Проверка должна сохранять дату, версию модели,
   эталон и причины решения.
2. Условия запуска кандидата: например, устойчивая accuracy ниже 0,7 на достаточной
   выборке либо устойчивое существенное смещение в нескольких проверках за месяц.
   Для оценки качества также нужны recall положительного класса, precision/F1,
   баланс классов и интервалы неопределённости. Одна accuracy может скрывать проблему.
3. При drift без достаточной обратной связи — сигнал на проверку данных,
   а не обучение на собственных прогнозах модели.
4. Зафиксировать новый набор с обратной связью, происхождение строк и версию кода.
   Разделить обучение и независимую проверку по времени и пациентам, не допуская
   попадания одного пациента в обе части. Не подбирать условия по тестовой выборке.
5. Обучить кандидата в отдельной задаче, сохранить артефакты и результаты.
   Предусмотреть блокировку параллельных запусков, паузу между переобучениями
   и проверку появления новых данных; перекрывающиеся 30-дневные окна зависимы.
6. Зарегистрировать кандидата как challenger и сравнить с основной моделью
   на одной независимой выборке, затем проверить в фоновой работе.
7. Назначать champion только после проверки качества, скорости и регрессий.
   Автоматический запуск обучения и автоматическая замена модели — отдельные решения.

Точный порог и минимальный объём для автоматического обучения требуют отдельного
согласования. Текущий CD запускает одноразовый стенд GitHub Actions; он сам не имеет
доступа к новым исследованиям на компьютере пользователя. Для планировщика нужно
выбрать место запуска с доступом к нужному снимку данных и Vault.
