# Секреты и запуск

В проекте нет `.env` и `env_file`. Compose получает необходимые значения от
`scripts.start_stack` через окружение дочернего процесса. Команда явно отключает
автоматическое чтение `.env` механизмом Compose.

## Локальный запуск с KeePassXC

```powershell
.\.venv\Scripts\python.exe -m scripts.start_stack --keepass-db "путь\к\vault-keys.kdbx"
```

При первом запуске создаётся постоянный Vault с файловым backend в Docker-томе
`vault_data`. Ключ unseal и bootstrap root-токен записываются в KeePassXC
под именем `DevOps_Project-Vault-devops_project`. Защищённое поле «Пароль» записи
содержит JSON с двумя ключами; его читает скрипт запуска. В открытые текстовые
файлы и логи ключи не записываются. Файл KDBX создайте заранее в KeePassXC вне
каталога проекта, задав мастер-пароль. Скрипт запрашивает его скрытым вводом
и передаёт CLI через stdin, не через аргументы командной строки.
Если база дополнительно защищена ключевым файлом, укажите `--keepass-key-file`.
Базы с авторизацией только ключевым файлом или YubiKey пока не поддержаны.
Перед изменением базы через CLI закройте её в графическом интерфейсе KeePassXC,
чтобы не оставлять несохранённые параллельные изменения.

При следующих запусках команда читает эту запись, разблокирует Vault и берёт
существующие реквизиты PostgreSQL из `secret/database/postgres`. Пароль БД
не генерируется заново. PostgreSQL получает его только в своём контейнере.
API и consumer получают разные пары AppRole role_id/secret_id, без пароля БД
и без root-токена в окружении. Обе политики разрешают только чтение двух путей:
`secret/data/database/postgres` и `secret/data/kafka/config`.

Удостоверения AppRole обновляются при управляемом запуске; прежние Secret ID
отзываются. Выданные токены имеют TTL 1 час (максимум 4 часа). Secret ID не
истекает самостоятельно, чтобы контейнер мог авторизоваться после перезапуска.
Клиент выполняет AppRole login при получении настроек, а не использует root-токен.
Docker-администратор может прочитать окружение контейнеров; эти удостоверения
не заменяют разграничение доступа к самому Docker-хосту.

После перезапуска Vault он запечатан. Повторите `scripts.start_stack`, чтобы
разблокировать его и восстановить сервисы. `docker compose restart` приложения
использует существующее окружение; `docker compose up` без команды настройки
не предназначен для создания новых контейнеров приложения.

Для команд работы с БД используйте уже запущенный контейнер, например:

```powershell
docker compose exec diabetes-api python -m src.db.export_feedback
```

Не удаляйте `vault_data` и запись KeePassXC: для восстановления
нужны и зашифрованное содержимое Vault, и ключ разблокировки. Автоматический
экспорт ключей в GitHub не выполняется. Для другого компьютера потребуется
отдельная инициализация или безопасный перенос хранилища вместе с ключами.

Однократный переход со старого `.env`:

```powershell
.\.venv\Scripts\python.exe -m scripts.start_stack --migrate-env --keepass-db "путь\к\vault-keys.kdbx"
```

Команда переносит только реквизиты БД в Vault, сохраняя пароль существующей БД.
После проверки API и контракта БД старый `.env` удаляется. При ошибке файл остаётся.

## GitHub Actions

В репозитории нужны четыре секрета:

| Имя | Назначение |
|---|---|
| DVC_YANDEX_USER | Логин хранилища моделей |
| DVC_YANDEX_PASSWORD | Пароль приложения WebDAV |
| DOCKERHUB_USERNAME | Логин Docker Hub |
| DOCKERHUB_TOKEN | Токен с правом публикации образа |

CI публикует `<DOCKERHUB_USERNAME>/devops_project:<SHA>`. CD скачивает этот же
образ и вызывает `scripts.start_stack --ci --no-build --check`. Временный Vault,
его bootstrap-ключи и пароль временной PostgreSQL создаются на один запуск.
Ключи остаются в памяти команды, пароль — в Vault и окружении только контейнера БД.
Все контейнеры и тома тестового стенда удаляются в завершающем шаге, в том числе
после ошибок. Постоянная БД пользователя в CD не используется.

GitHub Secrets не подгружаются автоматически при локальном запуске Compose.
Статические `POSTGRES_PASSWORD` и `VAULT_TOKEN` в GitHub для этого временного
стенда не нужны. При будущем развёртывании постоянного сервера потребуется
отдельная схема авторизации CI в его Vault; текущий CD — функциональный стенд.

## Граница текущей реализации

Это локальная учебная инфраструктура: Vault доступен на localhost, внутри Docker
используется HTTP, unseal настроен на один ключ. Перед размещением на сервере
нужны TLS, политика резервного копирования Vault, разделение административных
доступов и выбранный способ unseal/auto-unseal. Отказ от `.env` не означает, что
эти настройки production уже выполнены.

Проверка на отдельном локальном стенде (только с новыми томами):

```powershell
python -m scripts.start_stack --ci --check --project devops_verify --compose-file docker-compose.verify.yml --vault-url http://127.0.0.1:18201 --api-url http://127.0.0.1:18001
docker compose -p devops_verify -f docker-compose.yml -f docker-compose.verify.yml down -v
```

Ключи режима `--ci` не сохраняются. После проверки стенд следует удалить:
это не режим длительной эксплуатации или восстановления существующего Vault.
