## Нужно ли вручную запускать все три скрипта?

**Нет. Запуск обучения сейчас отдельный, но регистрация и первоначальная активация
уже включены в `scripts/start_stack.py`.**

| Этап | Кто запускает сейчас | Что происходит автоматически внутри |
|---|---|---|
| Обучение | Разработчик: `python -m src.train`; либо `dvc repro`, когда требуется повторить стадию | Подготовка данных, обучение кандидатов, оценка, выбор победителя внутри нового выпуска, сохранение файлов |
| Регистрация | `start_stack.py` вызывает `src.register_release models/current.json --apply`; возможен отдельный запуск | Проверка выпуска, импорт датасета, добавление запуска обучения и версий в БД |
| Первоначальная активация | `start_stack.py` вызывает `scripts.activate_model_release models/current.json --if-no-champion` | Если champion отсутствует, применяет рекомендацию выпуска; если уже есть — сохраняет действующие роли |
| Замена действующего champion новым выпуском | Отдельное явное действие: активация выбранного выпуска без `--if-no-champion` | Переназначение ролей в одной транзакции и запись аудита |

Точные вызовы находятся в [scripts/start_stack.py](../scripts/start_stack.py),
в функции `main()`, после запуска `scripts.update_database`.

Само появление новых исследований, снижение F1 или наступление следующего месяца
**не запускает обучение**. Планировщика переобучения и автоматического продвижения по метрикам сейчас нет.
CI загружает готовые артефакты из DVC; CD использует их на временном стенде GitHub Actions.
CD не переобучает модель и не обновляет автоматически стенд на твоём компьютере.

## 1. `src/train.py`: получить обученный выпуск

Файл: [src/train.py](../src/train.py). Главная функция — `train_release()`.

**На входе:**

- `config.ini`: расположение исходного датасета, доли разбиений и случайное зерно.
- `training.json`: список моделей, семейства алгоритмов, параметры, настройки предобработки и поиска параметров.
- Обычно `data/raw/diabetes.csv`; альтернативно `--feedback-snapshot` с путём к `data.csv` и соседними `dataset.json` и `lineage.json`.
- Код подготовки данных и построения Pipeline, версии библиотек и Git для записи происхождения выпуска.

**Что делает:**

1. Читает данные через [src/data_preprocessing.py](../src/data_preprocessing.py).
   Обычный датасет делится стратифицированно; снимок обратной связи — по пациентам,
   чтобы исследования одного пациента не попадали в разные части.
2. Через [src/pipelines.py](../src/pipelines.py) строит Pipeline:
   клиническая обработка → заполнение пропусков → при необходимости масштабирование → классификатор.
   Параметры этих преобразований обучаются на тренировочной части.
3. Обучает все модели из `training.json`. Если настроен поиск, использует `GridSearchCV`.
4. Считает метрики на validation и выбирает максимальный F1 **среди кандидатов этого выпуска**.
   При равенстве сохраняется порядок конфигурации.
5. Оценивает выбранного победителя на test и сохраняет выпуск.

**На выходе:**

```text
models/
  <release>/
    <model-name>/model.joblib    # обученный Pipeline каждой модели
    manifest.json              # описание всего выпуска
    source/                    # снимок использованного кода и настроек
  current.json                 # копия манифеста последнего опубликованного выпуска
reports/
  metrics.json
  selected_parameters.json
```

`release` создаётся из времени UTC и случайного идентификатора.
Версии отдельных моделей получают суффиксы `-m1`, `-m2` и т. д.
Манифест содержит пути и SHA256 артефактов, настройки, метрики, происхождение кода,
описание датасета, номера строк train/validation/test и `champion_version`.

Именно здесь впервые появляется **рекомендация** `champion_version`:
в выражении `max(records, key=lambda record: record["validation"]["f1"])`.
`train.py` не подключается к БД и не меняет действующую роль модели.
Он также не сравнивает победителя нового выпуска с текущим champion из БД.

## 2. `src/register_release.py`: внести выпуск в реестр БД

Файл: [src/register_release.py](../src/register_release.py).
Основные функции — `validate_release()` и `register_release()`.

**На входе:** путь к манифесту, доступные файлы моделей и исходного датасета.
Для записи дополнительно нужны доступ к PostgreSQL через Vault и флаг `--apply`.

**Что делает:**

1. Проверяет манифест, пути, контрольные суммы, разбиения данных и сохранённый код.
2. Загружает каждый Pipeline и проверяет возможность получить прогноз.
3. С `--apply` импортирует датасет через
   [src/db/load_raw_dataset.py](../src/db/load_raw_dataset.py).
4. Создаёт отсутствующий `training_runs`, затем отсутствующие `model_versions`.
   Настройки, метрики, пути и версии берутся из манифеста.

**На выходе:**

| Таблица | Что записывается |
|---|---|
| `datasets`, `dataset_rows` | Датасет и его строки |
| `training_runs` | Выпуск, связь с датасетом, конфигурация и происхождение |
| `model_versions` | Версии, артефакты, параметры и метрики; новая роль — `challenger` |
| `model_role_history` | Триггер фиксирует первоначальное назначение роли |

Без `--apply` скрипт выполняет только проверку и ничего не записывает в БД.
Повторная регистрация того же неизменённого выпуска сохраняет существующие версии и роли.
Сведения `recommended_champion` сохраняются в метаданных, но сами по себе не делают модель основной.

**У роли `challenger` уже есть рабочий смысл:** фоновый обработчик выбирает такие версии
для новых сообщений. Поэтому регистрация нового выпуска может добавить фоновые модели,
даже если основной champion ещё не заменён. Их файлы должны быть доступны consumer.
Старые исследования автоматически для новых версий не пересчитываются.

## 3. `scripts/activate_model_release.py`: применить роли выпуска

Файл: [scripts/activate_model_release.py](../scripts/activate_model_release.py).
Основная функция — `main()`. В проекте используется именно это имя файла.

**На входе:** манифест нужного выпуска, уже зарегистрированные версии в БД,
их доступные файлы и доступ к PostgreSQL.

**Что делает:**

1. Повторно проверяет выпуск и блокирует изменение таблицы моделей на время операции.
2. Если передан `--if-no-champion` и основная модель уже существует, завершает работу без смены ролей.
3. Проверяет соответствие зарегистрированных версий артефактам выпуска.
4. Сначала переводит все версии в `archived`, затем моделям выбранного выпуска назначает
   `challenger`, а версии из `champion_version` — `champion`.
5. Фиксирует одну транзакцию.

**На выходе:** обновлённые роли в `model_versions` и аудит в `model_role_history`.
Новые файлы моделей и новые прогнозы этот скрипт не создаёт.
Предыдущие версии вне выбранного выпуска остаются в архиве; строки и файлы не удаляются.

Архивирование и окончательное назначение происходят в одной транзакции:
другие запросы не видят промежуточного состояния «все в архиве».
Триггер [db/02_audit.sql](../db/02_audit.sql), функция `audit_model_role()`,
сохраняет сами переходы. Поэтому у двух моделей могут быть шесть записей истории:
две `NULL → challenger`, две `challenger → archived` и две с окончательными ролями.
Количество строк истории не равно количеству моделей.

## Что произойдёт с новым выпуском: пример

Допустим, в БД сейчас A — champion, B — challenger.

| Действие | Файлы выпуска | Роли в БД |
|---|---|---|
| Обучили C и D; C лучше D по validation F1 | Новый манифест рекомендует C | A остаётся champion; B — challenger |
| Зарегистрировали новый выпуск | Файлы не меняются | A — champion; B, C, D — challenger |
| `start_stack` вызвал активацию с `--if-no-champion` | Файлы не меняются | A уже существует, поэтому роли сохранены |
| Явно активировали выпуск C/D без этого флага | Файлы не меняются | C — champion; D — challenger; A и B — archived |

В последнем шаге сравнения F1 модели C с моделью A нет: скрипт исполняет явный выбор выпуска.

**`models/current.json` и текущий champion в БД — разные вещи.**
Первый описывает последний опубликованный обучением выпуск.
Работающий [src/app.py](../src/app.py) выбирает champion из БД, а
[src/kafka/shadow.py](../src/kafka/shadow.py) выбирает challenger из БД.
[src/model_registry.py](../src/model_registry.py) загружает Pipeline по записи версии.

## Как читать остальную цепочку

1. `start_stack.py` получает административные ключи из KeePass, запускает/разблокирует Vault,
   настраивает доступы, поднимает БД/Kafka, обновляет схему, регистрирует выпуск,
   при необходимости активирует его и запускает сервисы.
2. Браузерный `frontend/app.js` отправляет данные через `frontend/js/api.js` и Nginx в `src/app.py`.
   `src/auth.py` проверяет вход, `src/schemas.py` — данные запроса.
3. API выбирает champion, рассчитывает результат и публикует событие через `src/kafka/producer.py`.
   Подтверждение приёма Kafka ещё не означает завершение фонового расчёта.
4. `src/kafka/consumer.py` сохраняет основной результат и вызывает `src/kafka/shadow.py`:
   тот рассчитывает и сохраняет результаты challenger. Оба работают с БД.
5. `src/studies.py` отдаёт историю/карточку, принимает фактические исходы.
   `src/study_editing.py` обрабатывает исправления, а `src/feedback_dataset.py` создаёт
   проверяемый снимок подтверждённых исследований для следующего обучения.
6. `src/metrics_exporter.py` рассчитывает числовые показатели по БД.
   Prometheus собирает их и метрики процессов; Alloy отправляет метрики контейнеров
   в Prometheus, а журналы — в Loki. Grafana запрашивает эти хранилища.

Подготовленную аналитику `src/model_health_history.py` с выбором периода, дня/месяца
и версии модели схема отделяет от существующего потока scrape Prometheus.
Подключение её к новому разделу Grafana — отдельная работа; наличие Python-модуля
само по себе ещё не создаёт панели.

## Команды: что именно запускается

Ниже описаны интерфейсы скриптов; при подготовке схем они не выполнялись.

```powershell
# Обучение по настройкам проекта — создаёт новый выпуск файлов
.\.venv\Scripts\python.exe -m src.train

# Проверка последнего выпуска — без подключения и записи в БД
.\.venv\Scripts\python.exe -m src.register_release models/current.json
```

Для обучения на снимке в первую команду добавляется
`--feedback-snapshot data/feedback/<snapshot>/data.csv`.

В настроенном окружении с доступом к Vault и БД интерфейсы этапов такие:

```text
python -m src.register_release <manifest.json> --apply
python -m scripts.activate_model_release <manifest.json> --if-no-champion
python -m scripts.activate_model_release <manifest.json>
```

Последняя команда явно меняет роли, даже если champion уже есть.
`--apply` существует у регистрации; у активации такого флага нет.
В текущем локальном сценарии окружение подключений подготавливает `start_stack.py`,
а регистрацию/активацию он выполняет внутри контейнера API.
Новый выпуск должен также попасть в образы API и consumer: `Dockerfile` копирует `models/`
при сборке. Поэтому после обучения новые файлы на компьютере сами не появляются
в уже запущенных контейнерах; сценарий с `--no-build` не подходит для доставки нового выпуска.
