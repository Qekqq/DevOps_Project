## Основные команды

```powershell
.\.venv\Scripts\python.exe -m src.train
.\.venv\Scripts\python.exe -m src.register_release models/current.json
.\.venv\Scripts\python.exe -m src.db.load_dataset
.\.venv\Scripts\python.exe -m pytest tests -q
```

Обучение создаёт отдельный выпуск и обновляет `models/current.json`.
Статистики предобработки обучаются только на train. Выбор победителя использует
validation F1; test оценивается после выбора. Пространство поиска задаётся
в `training.json`. Для двух вариантов tuned выполняется GridSearchCV на train;
сейчас способ импутации фиксирован: median. Лучшие параметры и CV F1 записываются
в манифест и `reports/selected_parameters.json`. Сравнение validation-метрик
доступно через `dvc metrics show`; настройки поиска — через `dvc params diff`.

Чтобы в будущем сравнить медиану и среднее, добавьте в `search.param_grid`
нужной модели ключ `"imputer__strategy": ["median", "mean"]`.
Чтобы использовать только среднее без поиска способа заполнения, задайте
`preprocessing.imputation` равным `mean` и не добавляйте этот ключ в сетку поиска.
Новый запуск создаст отдельные версии; существующие pipeline не изменятся.

Команды регистрации и импорта без `--apply` только проверяют данные.
С `--apply` они записывают данные через подключение из Vault.
Регистрация добавляет challenger, но не переключает действующую champion.

## Прогнозы

API проверяет входные поля, выбирает champion и вызывает полный pipeline.
Нули у пяти измерений обрабатываются внутри pipeline; ноль беременностей сохраняется.
Успешная публикация подтверждает доставку в Kafka, а не завершение записи в БД.
Consumer сохраняет прогноз и последовательно выполняет фоновые challenger.
Уже сохранённые прогнозы при повторной доставке пропускаются.

Ошибка модели оставляет сообщение неподтверждённым. Устойчиво падающая модель
задерживает раздел очереди до исправления или перевода в archived.
При ошибке публикации API возвращает 503. Повторять запрос следует с теми же данными.
Другие показатели для того же пациента и даты дают 409.

## Снимки обратной связи

Для подготовленной БД команда `python -m src.db.export_feedback` создаёт снимок
подтверждённых исследований в `data/feedback/<sha256>/`. Снимок регистрируется в БД.
Обучающий `data.csv` содержит только восемь признаков и outcome. Идентификаторы
исследований и пациентов хранятся отдельно в `lineage.json` и используются только
для происхождения данных и разбиения. Контрольные суммы обоих файлов проверяются.

```powershell
.\.venv\Scripts\python.exe -m src.db.export_feedback
.\.venv\Scripts\python.exe -m src.train --feedback-snapshot data/feedback/<снимок>/data.csv
```

Вторая команда разделяет пациентов между выборками и передаёт группы пациентов
в кросс-валидацию. Доли задаются по группам и могут отличаться по числу строк.
Это проверка обобщения на других пациентов, не временное разбиение.
Если данных или классов недостаточно, обучение завершается с ошибкой.
Без аргумента обучение использует первоначальный CSV. Готовый снимок нужно
отдельно включить в версионирование DVC перед публикацией нового выпуска.

Структура БД описана в `src/db/models.py`; `db/01_schema.sql` генерируется
командой `python -m scripts.generate_schema`. Триггеры аудита находятся
в `db/02_audit.sql`; существующую БД обновляет `scripts/update_database.py`.
Модели доступны через DVC на Яндекс Диске: `python -m dvc pull models`.
CI запускается при push в `develop`/`main` и pull request в `main`: проверяет Python,
схему БД, JavaScript и тесты, собирает Python-образ и frontend. При pull request
образы не публикуются. При push они публикуются с тегом коммита; CI сохраняет
пакет `release-<SHA>` с digest образов и контрольными суммами конфигурации.
Тег `latest` для выкладки не используется.
CD запускается только после успешного CI ветки `main` через `workflow_run`.
CD разворачивает одноразовый стенд и запускает pytest из `tests/integration/`:
проверки входа через Nginx, API, Kafka, двух моделей, аудита БД, мониторинга и перезапуска Vault.
При обычном запуске pytest эти тесты пропускаются, поскольку им нужен отдельный стенд.
`start_stack --ci --check` подключает каталог тестов только к проверочному контейнеру;
в рабочий образ тесты не копируются.
После успешных проверок и удаления временного окружения CD передаёт пакет
локальному runner с меткой `devops-production`. Он обновляет приложение готовыми
образами без сборки исходников. Пакет проверяется по SHA и ID запуска CI; устаревший
коммит, не совпадающий с текущим `main`, не выкладывается.
Пароль тестовой БД и ключи Vault генерируются для каждого запуска и маскируются в логах.
GitHub Secrets: `DVC_YANDEX_USER`, `DVC_YANDEX_PASSWORD`,
`DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`. Временной БД не нужны постоянные пароли
из GitHub: она создаётся и удаляется в рамках одного задания CD.

Первичная настройка нового локального окружения (явная сборка исходников):
`python -m scripts.start_stack --local-build --keepass-db "путь/к/vault-keys.kdbx"`.
Vault хранит секреты в постоянном Docker-томе, API и consumer читают их через
отдельные AppRole. Ключ разблокировки и bootstrap-токен локального Vault хранятся
в зашифрованной базе KeePassXC вне каталога проекта.
После перезапуска Docker или Vault хранилище снова заблокировано (`sealed`).
В PowerShell выполните `.\start`: команда запускает существующие контейнеры,
при необходимости разблокирует Vault через KeePass и запускает зарегистрированный
runner. Исходники не собираются, AppRole не заменяются. Мастер-пароль вводится
скрыто; локально запоминается только путь к KeePass. Данные сохраняются.
Запуск ожидает готовности Grafana и API перед выполнением интеграционных проверок.
После запуска интерфейс доступен на `http://localhost:8080`, API — на
`http://localhost:8001`. Это локальный HTTP-режим; публичный HTTPS пока не настроен.

### Настройка автоматической выкладки

На GitHub: Settings → Actions → Runners → New self-hosted runner → Windows x64.
В локальном PowerShell выполните `.\setup-runner`. Команда скачивает официальный
архив, проверяет SHA256 и запрашивает краткоживущий регистрационный токен (не пароль
Vault). Если GitHub API не вернул SHA256, скопируйте сумму со страницы настройки runner.
Ожидаемое имя — `devops-production-windows`, метка — `devops-production`, статус — Idle.
Runner работает в фоне под текущей учётной записью Windows с доступом к Docker Desktop.
Windows-задание использует уже установленный Python из `.venv` проекта (или путь
`DEVOPS_PYTHON` в окружении runner). Установка Python через `setup-python` выполняется
только на временном окружении GitHub; локальная выкладка не запускает установщик.
После выключения ПК запускается вместе с `.\start`; отдельно — `.\runner`.

В Settings → Environments для `production` разрешите выкладку только из `main`.
В правилах `main` включите обязательный pull request и успешные задания CI
«Проверки проекта» и «Сборка и публикация Docker-образа». PR-проверки выполняются
только на GitHub-hosted runner; локальный runner предназначен для выкладки.

Пакеты конфигурации хранятся в `.local-history/deployment/releases`, отдельно от
рабочих исходников и checkout runner. Пароли в пакеты не записываются: существующие
AppRole и реквизиты PostgreSQL считываются из настроенных контейнеров в память.
При заблокированном Vault выкладка прекращается до изменения приложения.
Обновляются API, consumer, exporter, frontend и мониторинг. Vault, PostgreSQL и Kafka
не пересоздаются: при изменении их образов требуется отдельное обслуживание.
Тома БД и путь к существующим снимкам данных сохраняются.
Перед каждым обновлением, до изменения схемы БД и контейнеров, создаётся архив
PostgreSQL в `.local-history/deployment/backups` (на runner — внутри `DEVOPS_DEPLOY_HOME`).
Архив проверяется командой `pg_restore --list`; это проверка формата, не пробное
восстановление. Если копирование или проверка не удались, выкладка останавливается.
Незавершённые файлы имеют суффикс `.partial`. Путь к успешной копии выводится в CD
и записывается в `current.json` после успешной выкладки. Копии автоматически не
удаляются и в GitHub не отправляются. Восстановление остаётся ручным.
После запуска проверяются API, frontend, соединение consumer с Kafka и чтение метрик БД.
При сбое после начала обновления CD завершается ошибкой; автоматического отката
изменений схемы БД нет. Последний успешный выпуск записывается в `current.json`.

Для повторной проверки текущего `main` можно вручную запустить CI. Для повтора
только CD укажите ID успешного CI в поле `ci_run_id` (пакеты хранятся 30 дней).
Переход на HTTPS и публичное доменное имя выполняется отдельным изменением.

## Доступ и редактирование

`admin` имеет доступ к прогнозам, журналу, обратной связи и мониторингу.
`user` создаёт прогнозы и просматривает карточки независимо от автора, без редактирования.
Пароли хранятся в БД только как хеши, вход использует HttpOnly cookie и CSRF-токен.
Создание пользователя: `python -m scripts.create_user --help`.

Администратор может исправить восемь показателей в карточке. При изменении
хотя бы одного пересчитываются связанные модели, прежние данные сохраняются
в `study_edits`. Изменение только фактического исхода не запускает пересчёт.
Снимки обучения остаются неизменными. В журнале доступны фильтры по активным
моделям; по умолчанию выбрана Champion. Мониторинг использует реальные агрегаты PostgreSQL через Prometheus и Grafana.

## Резервные копии

`scripts/backup_database.py` создаёт архив PostgreSQL в игнорируемом `backups/`.
`scripts/verify_database_backup.py` проверяет восстановление архива во временной

Архивы не входят в Git и Docker-образы; удалять их следует по сроку хранения.

## Снимок исследований за период

Выгрузка включает только исследования с заполненной обратной связью (`0` или `1`).
Фильтр применяется к дате исследования; обе границы включены. Любую границу можно
не задавать. Применённые даты сохраняются в `dataset.json` рядом с CSV.

```powershell
.\.venv\Scripts\python.exe -m src.db.export_feedback --name "Исследования за сентябрь 2026" --date-from 2026-09-01 --date-to 2026-09-30
```

CSV сохраняется в `data/feedback/<идентификатор>/data.csv`. Создание снимка не
запускает обучение. Администратор также может создать и скачать снимок кнопкой
в журнале прогнозов. Для снимка учитывается только период дат; остальные фильтры
журнала на него не влияют. Перед созданием открывается окно для ввода названия
(1–100 символов). Название сохраняется в `datasets.dataset_name`, в `dataset.json`
и используется в имени скачиваемого CSV. Технический каталог по-прежнему определяется
контрольной суммой. Одинаковые данные с разными названиями образуют отдельные снимки;
повтор с теми же данными, периодом и названием возвращает существующий снимок.
Прежние снимки остаются совместимыми и сохраняют свои названия.
## Разные способы заполнения признаков одной модели

Каждая модель в `training.json` имеет собственный блок `preprocessing`.
Например, для нового варианта модели можно задать:

```json
"preprocessing": {
  "imputation": "median",
  "imputation_by_feature": {
    "glucose": "mean",
    "insulin": "mean"
  },
  "scale": true
}
```

Здесь глюкоза и инсулин заполняются средними, остальные признаки — медианами.
Нули пяти измеряемых показателей предварительно считаются пропусками;
ноль беременностей остаётся настоящим значением. Все статистики вычисляются
внутри pipeline только на обучающей части, в том числе внутри каждого шага
кросс-валидации. Они сохраняются в `model.joblib` и применяются при прогнозе.

Чтобы автоматически выбрать способ заполнения конкретного признака, при
использовании `imputation_by_feature` добавьте в `search.param_grid`, например,
`"imputer__glucose__strategy": ["median", "mean"]`. Без индивидуальных настроек
по-прежнему применяется общий параметр `imputer__strategy`.

Для нового эксперимента добавьте модель с новым именем в `training.json`,
скопировав настройки выбранного семейства, затем измените её `preprocessing`
и запустите обучение. Выпуск получает новый идентификатор, а конфигурация и
результаты поиска сохраняются в его manifest. Текущие два кандидата используют
только медиану; приведённый пример не меняет их настройки автоматически.

## Мониторинг

`src/monitoring.py` рассчитывает матрицу ошибок на общей группе исследований:
есть фактический исход и сохранены прогнозы всех активных моделей. Неразмеченные
исследования не считаются отрицательными. Главная метрика — Recall (чувствительность),
дополнительные — Precision и F1. Для собственных панелей экспортируются матрица 2×2 и стандартный
`sklearn.metrics.classification_report` по выбранной модели: оба класса, accuracy,
macro avg, weighted avg и support. При неопределённой метрике отображается «—».
Целевой Recall и допустимое число
ложноположительных результатов пока не установлены. Мониторинг не меняет порог
классификации, способ выбора Champion или сохранённые метрики обучения.

Внутренний `metrics-exporter` читает БД в одной read-only транзакции,
используя сервисные реквизиты API из Vault. Экспортируются только агрегаты по версиям
моделей, без пациентов и входных показателей. Prometheus опрашивает его раз в 30 секунд.
Это gauge-метрики: после исправления показателей или исхода значения могут уменьшиться.
При недоступности БД старые агрегаты не выдаются как свежие.

Grafana открывается в разделе «Мониторинг» и по `/grafana/` того же сайта.
Nginx проверяет действующую сессию и роль admin при каждом запросе, затем передаёт
сформированную сервером идентичность в Grafana auth proxy. Отдельных публичных портов
Prometheus, Grafana, Loki, Alloy и exporter нет. В Grafana администратор приложения получает
роль Editor и может создавать и сохранять дашборды в интерфейсе Grafana.
Источники Prometheus и Loki задаются файлами в `monitoring/grafana/provisioning/datasources/`.
Готовые файловые дашборды удалены; автоматическая загрузка дашбордов отключена.
Пользовательские дашборды сохраняются в томе `grafana_data`, переживают перезапуск
контейнера, но не сохраняются автоматически в Git. Для переноса экспортируйте JSON.
В разделе «Мониторинг» пункт «Работа приложения» показывает сохранённый дашборд
с UID `fastapi-observability`. Его адрес задан в `frontend/js/monitoring.js`.
После редактирования нажмите Save в Grafana и заново откройте мониторинг.
На новом стенде этот дашборд нужно импортировать с тем же UID.
Интервал источника Prometheus в Grafana совпадает с интервалом сбора — 30 секунд.

Метрики охватывают текущие записи БД за всё время. Выбор периода в Grafana меняет
период наблюдений Prometheus, а не даты исследований. Исторические точки появляются
только после подключения мониторинга. Обе модели сравниваются на одинаковой группе,
но неполная обратная связь и малый объём данных могут смещать оценку качества.

Для собственных дашбордов доступны запросы, отдельно возврат сохранённого
прогноза, HTTP 5xx и отклонённые запросы 401/403/409/422/429, p50/p95 времени ответа,
p95 выполнения моделей и фоновой обработки. Время выполнения модели не включает
загрузку артефакта и не измеряется при возврате сохранённого результата.
Счётчики запросов оцениваются Prometheus между замерами; это не точный журнал аудита.
Неполные исследования — текущие записи без результата хотя бы одной активной модели,
а не Kafka consumer lag. После смены активной версии сюда могут попасть старые записи.

Alloy через встроенный cAdvisor собирает CPU и память всех контейнеров текущего
Compose-проекта, включая Kafka, PostgreSQL, Vault, frontend и мониторинг. Метрики
передаются в Prometheus каждые 30 секунд через внутренний `/api/v1/write`.
Метка `job="docker-containers"` выделяет этот сбор, `service` содержит имя сервиса.
Другие Compose-проекты отфильтровываются до отправки. Для чтения cgroup Alloy запускается
в privileged-режиме с пространством cgroup хоста, системными каталогами и Docker socket.
Монтирование socket с `:ro` не ограничивает команды Docker API. Порты Alloy и Prometheus
не публикуются наружу. В Docker Desktop измеряются Linux-контейнеры внутри его VM.

CPU в процентах одного ядра (100% — одно занятое ядро, возможны значения выше 100%):

```promql
100 * sum by (service) (
  rate(container_cpu_usage_seconds_total{job="docker-containers"}[5m])
)
```

Память без неактивного файлового кеша: `container_memory_working_set_bytes{job="docker-containers"}`.
История этих метрик начинается с подключения cAdvisor. Старые метрики `diabetes_container_*`
из `src/telemetry.py` остаются доступны для API, consumer и exporter; их память включает
файловый кеш. Метрики API рассчитаны на один процесс Uvicorn, как в текущем Dockerfile.

События приложения пишутся в JSONL: действие, время, уровень, сервис, внутренний ID
пользователя, код ответа и ID запроса. Последний связывает API с обработкой Kafka,
но не используется как метка Prometheus или Loki. Пароли, cookies, тело запроса,
код пациента и медицинские показатели в эти события не включаются. Alloy читает
только `*.jsonl` из общего тома и отправляет их в Loki. Старые диагностические
`app.log` и stdout сторонних библиотек не собираются. Подробный аудит правок остаётся в БД.

История Prometheus хранится до 30 дней с ограничением 1 GB; Loki — 7 дней.
Срок хранения Loki не является ограничением размера диска. JSONL ротируются:
5 MB на файл и две резервные копии на сервис. Для новых сервисов заданы лимиты CPU
и памяти, данные и позиции чтения хранятся в Docker-томах.
`tests/integration/test_monitoring_stack.py` проверяет общую выборку, доставку метрик
и событий в Loki, доступ администратора, отказ роли user и отказ после выхода.
