# Diabetes Predict — MLOps

Исследование определяется кодом пациента и датой. Прогноз определяется исследованием
и версией модели. Обратная связь относится к исследованию и используется всеми моделями.

## Структура

| Путь | Назначение |
|---|---|
| `data/raw/diabetes.csv` | Неизменённый исходный датасет |
| `config.ini` | Пути и настройки разбиения |
| `training.json` | Алгоритмы и гиперпараметры |
| `src/datasets.py` | Проверка исходных данных |
| `src/data_preprocessing.py` | Разбиение без заполнения пропусков |
| `src/pipelines.py` | Полная предобработка и классификаторы |
| `src/train.py` | Обучение, оценка и сохранение выпуска |
| `models/current.json` | Манифест последнего выпуска |
| `models/<release>/` | Pipeline, метрики, происхождение данных и снимок кода |
| `src/register_release.py` | Проверка и регистрация выпуска |
| `src/model_registry.py` | Проверка артефактов и кеш моделей |
| `src/app.py` | API с выбором champion из БД |
| `src/kafka/` | Доставка результатов и фоновые challenger |
| `src/db/` | Репозитории, модели хранения и импорт исходного датасета |
| `db/` | Сгенерированная схема и триггеры аудита |
| `tests/` | Проверки поведения компонентов |
| `notebooks/` | Анализ данных, эксперименты, подбор параметров и выпуск через общие модули |

## Основные команды

```powershell
.\.venv\Scripts\python.exe -m src.train
.\.venv\Scripts\python.exe -m src.register_release models/current.json
.\.venv\Scripts\python.exe -m src.db.load_dataset
.\.venv\Scripts\python.exe -m pytest tests -q
```

Обучение создаёт отдельный выпуск и обновляет `models/current.json`.
Статистики предобработки обучаются только на train. Выбор победителя использует
validation F1; test оценивается после выбора. Пространство поиска задаётся
в `training.json`. Для двух вариантов tuned выполняется GridSearchCV на train;
сейчас способ импутации фиксирован: median. Лучшие параметры и CV F1 записываются
в манифест и `reports/selected_parameters.json`. Сравнение validation-метрик
доступно через `dvc metrics show`; настройки поиска — через `dvc params diff`.

Чтобы в будущем сравнить медиану и среднее, добавьте в `search.param_grid`
нужной модели ключ `"imputer__strategy": ["median", "mean"]`.
Чтобы использовать только среднее без поиска способа заполнения, задайте
`preprocessing.imputation` равным `mean` и не добавляйте этот ключ в сетку поиска.
Новый запуск создаст отдельные версии; существующие pipeline не изменятся.

Команды регистрации и импорта без `--apply` только проверяют данные.
С `--apply` они записывают данные через подключение из Vault.
Регистрация добавляет challenger, но не переключает действующую champion.

## Прогнозы

API проверяет входные поля, выбирает champion и вызывает полный pipeline.
Нули у пяти измерений обрабатываются внутри pipeline; ноль беременностей сохраняется.
Успешная публикация подтверждает доставку в Kafka, а не завершение записи в БД.
Consumer сохраняет прогноз и последовательно выполняет фоновые challenger.
Уже сохранённые прогнозы при повторной доставке пропускаются.

Ошибка модели оставляет сообщение неподтверждённым. Устойчиво падающая модель
задерживает раздел очереди до исправления или перевода в archived.
При ошибке публикации API возвращает 503. Повторять запрос следует с теми же данными.
Другие показатели для того же пациента и даты дают 409.

## Состояние перехода

Для подготовленной БД команда `python -m src.db.export_feedback` создаёт снимок
подтверждённых исследований в `data/feedback/<sha256>/`. Снимок регистрируется в БД.
Обучающий `data.csv` содержит только восемь признаков и outcome. Идентификаторы
исследований и пациентов хранятся отдельно в `lineage.json` и используются только
для происхождения данных и разбиения. Контрольные суммы обоих файлов проверяются.

```powershell
.\.venv\Scripts\python.exe -m src.db.export_feedback
.\.venv\Scripts\python.exe -m src.train --feedback-snapshot data/feedback/<снимок>/data.csv
```

Вторая команда разделяет пациентов между выборками и передаёт группы пациентов
в кросс-валидацию. Доли задаются по группам и могут отличаться по числу строк.
Это проверка обобщения на других пациентов, не временное разбиение.
Если данных или классов недостаточно, обучение завершается с ошибкой.
Без аргумента обучение использует первоначальный CSV. Готовый снимок нужно
отдельно включить в версионирование DVC перед публикацией нового выпуска.

БД пересоздана по согласованной схеме: [структура и запуск](docs/database.md).
Модели доступны через DVC на Яндекс Диске: `python -m dvc pull models`.
CI запускает тесты, публикует образ в GHCR с тегом коммита, затем вызывает CD.
CD разворачивает временный стенд, проверяет API, Kafka, две модели и аудит БД.
Это проверочное развёртывание, а не публикация на постоянный сервер.
Пароли тестовой БД и Vault генерируются для каждого запуска и маскируются в логах.
GHCR использует встроенный GITHUB_TOKEN; DockerHub secrets не требуются.

Секреты не коммитятся. `.env` служит для локального запуска инфраструктуры;
приложение получает параметры PostgreSQL и Kafka из Vault.
# Снимок исследований за период

Выгрузка включает только исследования с заполненной обратной связью (`0` или `1`).
Фильтр применяется к дате исследования; обе границы включены. Любую границу можно
не задавать. Применённые даты сохраняются в `dataset.json` рядом с CSV.

```powershell
.\.venv\Scripts\python.exe -m src.db.export_feedback --date-from 2026-09-01 --date-to 2026-09-30
```

CSV сохраняется в `data/feedback/<идентификатор>/data.csv`. Создание снимка не
запускает обучение. Пока доступен запуск командой; кнопка администратора и
защищённые API-методы создания и скачивания снимков ещё не реализованы.
# Разные способы заполнения признаков одной модели

Каждая модель в `training.json` имеет собственный блок `preprocessing`.
Например, для нового варианта модели можно задать:

```json
"preprocessing": {
  "imputation": "median",
  "imputation_by_feature": {
    "glucose": "mean",
    "insulin": "mean"
  },
  "scale": true
}
```

Здесь глюкоза и инсулин заполняются средними, остальные признаки — медианами.
Нули пяти измеряемых показателей предварительно считаются пропусками;
ноль беременностей остаётся настоящим значением. Все статистики вычисляются
внутри pipeline только на обучающей части, в том числе внутри каждого шага
кросс-валидации. Они сохраняются в `model.joblib` и применяются при прогнозе.

Чтобы автоматически выбрать способ заполнения конкретного признака, при
использовании `imputation_by_feature` добавьте в `search.param_grid`, например,
`"imputer__glucose__strategy": ["median", "mean"]`. Без индивидуальных настроек
по-прежнему применяется общий параметр `imputer__strategy`.

Для нового эксперимента добавьте модель с новым именем в `training.json`,
скопировав настройки выбранного семейства, затем измените её `preprocessing`
и запустите обучение. Выпуск получает новый идентификатор, а конфигурация и
результаты поиска сохраняются в его manifest. Текущие два кандидата используют
только медиану; приведённый пример не меняет их настройки автоматически.
